Resume Review Graph

Eight nodes run in a fixed order, with no conditional edges, no interrupt and no checkpointer: one PDF upload, one run. Step ⑤ takes the longest; it reviews six dimensions with concurrent LLM calls through asyncio.gather.

The graph runs in the background and the API does not wait for it; the frontend polls with the review_id. From backend/api/v1/resume.py.

Six review dimensions

Each dimension is one LLM call that returns a score from 0 to 100. A dimension that fails twice scores 50, asks for manual review, and sets fallback_used. Overall score = Σ score × weight.

DimensionWeightFocus
Project depth30%
Metrics, reasons for technical choices, personal contribution, problems solved
Tech match25%
Skills match the role's keywords and are backed by real use in experience
Writing15%
Strong action verbs, consistent tense, no pronouns, typos or buzzwords
Structure15%
Length, reverse-chronological order, ATS-friendly layout, no protected personal details
Quantification10%
Numbers such as performance, user counts and improvement percentages
Credibility5%
No exaggeration; depth matches years of experience; plausible timeline

Nodes

① upload_to_minio
Skipped in local mode; returns an empty dict. Uploads the PDF once MinIO is wired in.
② download_pdf
Skipped in local mode. With object storage, downloads the PDF when the local file is missing.
③ extract_text
Runs PyMuPDF in a thread pool on up to 5 pages, rebuilds visual rows, reads two-column layouts left then right, and caps the text at 12,000 characters for every later node. Warns under 200 characters (likely a scanned PDF).
④ extract_structured
The LLM extracts name, education, skills, projects and work experience. After two failures it falls back to an empty structure and sets fallback_used.
⑤ run_six_dimensions
Reviews six dimensions in parallel. Code adds the computed years of experience and role order to the prompt, writes back each dimension's name and weight, and computes the weighted score.
⑥ diagnose_issues
A think step assesses the resume as a whole (allowed to fail), then the LLM writes an issue list with locations and fixes, sorted by priority. On failure it reuses the dimension issues and sets fallback_used.
⑦ generate_summary
Turns the scores and high-priority issues into highlights, core improvements, an overall comment and role fit. On failure it returns a default assessment and sets fallback_used.
⑧ save_results
Writes structured data, scores, issues and summary to the JSONB columns of resume_reviews, sets status to done, deletes the temp PDF, and returns fallback_used as recorded by the earlier nodes.

Unlike the QA agent, every LLM step here has a fallback, so one failed dimension or node does not fail the whole review; fallback_used tells the caller the result is partial. Only a PDF parsing or database error marks the background task as failed.
