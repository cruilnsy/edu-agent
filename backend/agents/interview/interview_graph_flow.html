Mock interview agent graph

The graph has no loop and no interrupt. Each candidate message runs it once from START to END; the interview's progress lives in the state, which the checkpointer keeps per thread between requests. The conversation loop is in the API, and the five interview stages are driven by the current_stage field.

One turn

Seven nodes. Each turn takes one branch; the diamond is the conditional route after check_stage, not a node. The answer is graded before the stage check, so it is graded against the question it answers even when the stage then changes.

Stage machine

How current_stage changes; check_stage decides on every turn. These are not graph edges. When a stage changes, its turn count, follow-up count and current question are reset. Turns count candidate messages.

An end request is a whole-message pattern such as "can we end the interview" or "I need to leave", so the word "end" inside an answer does not count. Without resume projects, the project stage asks from what the candidate said and moves on after 2 turns. With an empty question bank, the technical stage is skipped.

API lifecycle

Each request runs the graph once. The stream endpoint pushes the interviewer's reply as SSE tokens, then a done event. From backend/api/v1/interview.py; every query is scoped to the caller's tenant and student.

The four conversation stages

② labels each answer excellent, adequate, weak or no_answer. ④ uses the label to choose a follow-up or the next question; at most 2 follow-ups per question or project.

The five report dimensions

At the end, the LLM scores each dimension 0–100 from the summary and the transcript (the most recent 20,000 characters). The overall score is the weighted average, computed in code.

Nodes

① load_context
On the first request, initializes the state and loads four things with asyncio.gather. LLM questions come first, then the DB bank for the position's track, with near-duplicates removed. If generation fails, the DB bank alone is used. Later requests only read the summary.
② evaluate_answer
Counts the message. Technical and project answers get one structured grade (analysis, then label) against the interviewer's last message. "I don't know" skips the LLM. A failed grade counts as adequate. Answers that address the interviewer are flagged.
③ check_stage
Ends the interview on an end request or the turn limit; otherwise moves on when the stage's maximum is reached, or its minimum is reached and its content is covered with no follow-up due.
④ generate_response
A planner per stage decides what to say and which state to update; then one LLM call writes the reply. If the call fails, a fixed reply still asks the next question. Candidate text is wrapped in <candidate_answer> tags.
⑤ generate_report
Structured five-dimension report, retried once on an empty or invalid reply. The overall score is the weighted average of the dimension scores. If both attempts fail, a report marked fallback with no score.
⑥ save_report
Saves the report and score and sets the session to finished, only while it is in_progress, so a report is never overwritten.
⑦ save_memory
Where both branches meet. Every 10 turns, merges the old summary with the dialogue and saves it to interview_sessions.summary.

Known limit: the interview state lives in process memory. After a backend restart, the next message finds no state and the interview starts again from the warmup. Production should use AsyncPostgresSaver.
